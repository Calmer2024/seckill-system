# P0 可观测能力与运行说明

实施日期：2026-10-03。可观测交互位于现有 `performance/web` 压测工作台的“指标与监控”视角，无新增前端项目，也未改动秒杀商城 `frontend`。

## 已交付

- `packages/seckill-observability` 0.1.0 共享 Python 包，供四服务和两个 worker 使用。
- 单行 JSON 应用日志，含服务、环境、版本、容器实例、PID、事件和业务状态字段。同步业务日志自动注入 request_id；异常堆栈保持在一个 JSON 字符串中。
- ContextVar 上下文与纯 ASGI 中间件；同步线程池、流式响应和异常路径清理；request ID 校验长度及字符集；订单到库存的 httpx 请求继续传播 ID。
- 路由标签使用代码定义的模板，未匹配请求归为 `__unmatched__`，未知 HTTP 方法归为 OTHER，动态库存错误码映射到固定结果集合。
- Nginx JSON access log 与入口生成的 request ID；不记录请求查询串。应用关闭重复 Uvicorn access 日志，保留结构化错误与生命周期日志。
- 两个 worker 的独立内部 `:9106/metrics`，逐任务线程健康、成功轮询时间、成功业务进度、异常退出计数与整体 readiness。
- 消费者使用有超时的 poll；空闲轮询更新健康，不虚增业务进度。保留业务处理后提交 offset 的顺序，处理失败不提交。
- 后台任务未处理异常后明确标记不健康并记录堆栈，不自动吞错重试。另一个线程仍运行时能观测到部分任务失败。
- Prometheus worker jobs 及三个规则；工作台只读状态 API、5 秒后端缓存和视角可见时 10 秒刷新。
- Docker 根构建上下文正确打包共享包；Prometheus 客户端固定 0.21.1；应用容器日志大小轮转。

HTTP 指标名称及旧 service 标签保持兼容，商品两容器各 4 个进程仍采用现有 multiprocess 汇总。P0 不增加商品进程 Gauge，因此没有新增 live Gauge 退出清理契约。

## 页面与 API

入口 `http://127.0.0.1:8099/?view=metrics#runs`，选择任务后查看“指标与监控”。

上方“指标快照”仍属于所选历史任务；下方“环境当前状态”属于本地环境，显示 Prometheus 来源、采集时间、API 目标与 worker 的各任务状态。不按所选历史任务模式过滤当前 worker，也不把当前数据写回历史报告。

只读接口 `GET /api/performance/observability/status` 固定查询本地 Prometheus，不接受用户传入查询语句或目标 URL。服务端配置 `PERFORMANCE_PROMETHEUS_URL` 默认 `http://127.0.0.1:9090`，是受信运行配置。请求超时 2.5 秒、响应大小上限 2MB；客户端刷新超时 6 秒。

状态区别：

| 状态 | 含义 |
|---|---|
| 正常 | 目标最近 30 秒采集成功；worker 任务仍运行且最近完成健康轮询 |
| 未配置采集 | 当前 Prometheus 没有对应 job/目标 |
| 未接入任务指标 | 目标可抓取，但没有所需任务指标 |
| 不可用 | 抓取目标失败 |
| 采集已过期 | 最后采集超过新鲜度预算，不能代表当前状态 |
| 后台任务异常 | 一个或多个任务已经退出或轮询停滞 |
| 部分采集异常 | 目标查询成功，但任务指标查询失败 |
| 采集不可用 | Prometheus 或控制器查询失败 |

业务进度显示“无记录”意味着进程启动后尚无成功业务处理，不能据此判定线程故障。异常退出次数是进程内 Counter，重启后重置；历史增长应使用 Prometheus increase。前端离线时保留最后已知结果并显示采集时间和刷新失败。

## 配置与启动

服务运行依赖 Python 3.12+。开发环境先安装共享包：

```powershell
py -3.12 -m venv .venv
./.venv/Scripts/python.exe -m pip install -e ./packages/seckill-observability
# 各服务还需安装自身 requirements.txt；保持 app 包路径彼此独立。
```

共享包不能再通过仅服务目录的 Docker build context 构建。根 Compose 已配置根上下文与对应 Dockerfile；直接构建示例为 `docker build -f order_service/Dockerfile .`。

更新本地分布式模式的相关服务：

```powershell
docker compose --profile monitoring build user_service product_service_1 product_service_2 order_service order_worker inventory_service inventory_worker
docker compose --profile monitoring up -d --no-deps user_service product_service_1 product_service_2 order_service order_worker inventory_service inventory_worker
./performance/web/start-web.ps1 -Background
```

若当前环境是基线模式，应在 build/up 命令中使用原来的 `-f docker-compose.yml -f performance/config/docker-compose.baseline.yml`，不要在部署 P0 时顺带改变业务开关。已有控制器进程需要重启才能读取新增 Python 路由；启动脚本发现旧健康进程时不会自动升级。

Prometheus 与 Nginx 配置为挂载文件，先校验再重载：

```powershell
docker exec seckill_prometheus promtool check config /etc/prometheus/prometheus.yml
Invoke-WebRequest -Uri http://127.0.0.1:9090/-/reload -Method Post
docker exec seckill_nginx nginx -t
docker exec seckill_nginx nginx -s reload
```

两个 worker 的指标端口仅内部网络开放，无宿主机端口映射。Docker healthcheck 检查 worker_ready；任何关键线程退出会使容器 unhealthy。容器不会因 unhealthy 自动重启；修复与恢复策略属于可靠性改造，避免无幂等保障的自动重放。

配置字段：

| 配置 | 默认与意义 |
|---|---|
| OBSERVABILITY_ENVIRONMENT | local；当前控制台固定为本地环境，不支持多环境切换 |
| SERVICE_VERSION | unknown；部署前可传 Git SHA，未提供时不伪造版本 |
| SERVICE_INSTANCE_ID | 容器 hostname |
| LOG_LEVEL | INFO（用户服务环境变量，其余现有 settings） |
| LOG_USER_ID_HASH_KEY | 未设置时不输出 user_id；设置后输出 HMAC user_hash |
| WORKER_METRICS_PORT | 9106 |

脱敏覆盖 Bearer、常见密钥字段（包括 JSON/字典形式）、有凭据的 URL、邮箱、常见手机号与 URL 查询串。日志 schema 不接收请求体、authorization/cookie、原始 path、keyword 和 cache_key。规则脱敏不能识别所有无结构秘密，调用方仍必须遵守禁止记录敏感业务数据的约束。

## 排障 runbook

### WorkerTargetDown

检查 worker 容器状态、启动日志及内部指标端口。target down 时不要把上次抓取的 alive 当当前值。检查 Kafka 连接、主题初始化或数据库配置导致的启动退出。修复后受控重启，再确认全部任务指标为 1。

### WorkerTaskDown

按 role 找 `worker.task_exited`，消费者失败还有 `consumer.process_failed` 和 topic/group/partition/offset/order_id；发布失败有 `outbox.publish_failed` 与 outbox_record_id/订单/attempt。P0 的 outbox_record_id 是原有表行 ID，并非跨分片全局 event_id。检查原始异常，修复依赖或业务错误后再恢复。不要未经处理直接跳过消息或提交失败 offset。

### WorkerLoopStalled

确认线程是否被数据库、Kafka send/flush/commit 等调用阻塞。规则在成功轮询/发送尝试超过 60 秒且持续 30 秒后触发；UI 使用 90 秒阈值提示停滞，两者在启动与连续超时窗口边界上可能略有差异。成功空闲 poll 每秒更新时间，因此正常无流量不报警。业务成功时间长期不变，只作为排障证据，不单独触发失活规则。

规则当前由 Prometheus 评估，可查询 pending/firing；P0 没有通知通道和 Alertmanager，也不宣称已有通知交付。完整路由和通知闭环在 P3 接入。

## 验证记录与能力边界

已验证并发上下文隔离、同步线程池传播、流式响应、500/404 路由和错误头、日志脱敏、任务异常健康、指标 HTTP 端口、真实消费者循环的 commit 边界及上下文清理、httpx 下游 request ID、四进程指标汇总、状态缺失/过期/采集失败与缓存。Prometheus 规则序列测试验证目标失败、线程失败与空闲消费者不误报；原报告生成回归通过。

构建四类服务和两个 worker 镜像，并在隔离无网络容器中执行契约测试。更新本地现有基线应用容器后，两个 worker 的五个任务、全部 API targets 和 Docker readiness 实际正常；验证网关→商品业务日志/HTTP 响应 request ID 一致、两个随机用户 404 共用 __unmatched__ 指标模板。

本次未发起压测，也未验证生产容量。现有业务库存并发、支付模拟及消息可靠性问题没有被 P0 修复。Trace ID/span ID 字段预留但不会生成伪 trace；OTel SDK、Collector、Tempo、Loki、持久化异步上下文分别在后续阶段接入。
