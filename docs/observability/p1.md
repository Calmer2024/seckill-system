# P1 同步分布式追踪

实施日期：2026-10-03。界面位于现有 `performance/web` 压测平台的“指标与监控”视角。商城 `frontend` 没有参与本阶段开发。

## 已交付与边界

- 四个 API 服务使用共享包 0.2.0，接入 FastAPI、httpx、SQLAlchemy；有 Redis 依赖的服务接入 Redis 命令追踪。
- 手工业务 span 为 `order.submit`、`inventory.reserve`、`inventory.redis_reserve`。Redis 库存开关关闭时不会伪造 Lua span。
- 内部 HTTP 使用 W3C traceparent/tracestate，日志自动关联当前 trace_id/span_id，响应提供 `X-Trace-ID`。公网 Nginx 清除传入的 traceparent/tracestate/baggage，由首个 API 创建链路，防止外部请求强制全采样。内部调用保持父子关系；不传播 baggage。
- Collector 提供内存限流、批处理、有限重试和独立卷的持久导出队列，Tempo 使用 WAL、本地块存储和 24 小时保留。两个组件均有容器内存上限，查询与健康端口仅绑定本机。
- SDK 导出和 Collector 入库分别做属性白名单；移除 SQL 文本、参数、Redis 键值、请求 URL/查询串、请求体、鉴权字段和异常堆栈。详细异常仍通过 P0 的脱敏 JSON 日志定位。
- 工作台支持服务、最近 5/15/60 分钟、最短 span 耗时、错误 span 筛选；Trace ID 精确定位；父子层级、相对起点、耗时瀑布和白名单属性。列表最多 50 条，详情最多 1000 条原始 span，4 MiB 响应限制，2.5 秒后端查询超时。重复 span ID 合并展示。
- Collector、Tempo 的实际 Prometheus 采集目标加入环境状态表；SDK 提供 `trace_export_batches_total{result="success|failure"}`。Tempo 可查询不代表所有请求已被采样或导出。
- `run-test.ps1 -WithMonitoring` 自动添加可观测 Compose 覆盖文件，保留 baseline/distributed 模式配置。

本阶段只覆盖同步 HTTP 链路。Kafka headers、Outbox 中持久化上下文、消费者恢复与重试 links 属于 P2，两个 worker 尚未初始化追踪 SDK。集中日志检索与告警通知属于 P3。当前单机存储不提供生产高可用、对象存储、租户鉴权或磁盘硬配额；生产容量与权限边界仍需后续验收。

## 配置与部署

依赖组合固定为 OpenTelemetry SDK/OTLP HTTP 1.45.0、instrumentation 0.66b0、SQLAlchemy 2.0.35；Python 3.12。SQLAlchemy 插件声明支持 `<2.1.0`，因此不能继续使用无上限的 `sqlalchemy>=2.0.0`。用户服务保持原有 FastAPI/httpx 版本，其余服务将已验证的 FastAPI 0.142.2、Uvicorn 0.54.0、Redis 8.1.0 等直接运行依赖固定在 requirements 中，防止下次构建自动漂移。

| 配置 | 默认值 | 含义 |
|---|---|---|
| SECKILL_TRACING_ENABLED | false；覆盖文件设为 true | 显式启用追踪 |
| SECKILL_TRACE_SAMPLE_RATIO | 0.1 | 新根链路 10% 头采样；内部子 span 继承父级 |
| OTEL_EXPORTER_OTLP_TRACES_ENDPOINT | http://otel-collector:4318/v1/traces | 服务内部 OTLP HTTP 地址 |
| OBSERVABILITY_ENVIRONMENT | local | 资源与日志环境 |
| SERVICE_VERSION | unknown | CI/发布时应提供实际构建版本 |
| PERFORMANCE_TEMPO_URL | http://127.0.0.1:3200 | 控制器固定后端，浏览器不能覆盖 |

保持当前基线配置启动，不能省略 baseline 覆盖文件：

```powershell
docker compose -f docker-compose.yml -f performance/config/docker-compose.baseline.yml -f docker-compose.observability.yml --profile monitoring up -d --build
.venv\Scripts\python.exe performance/web/server.py --host 127.0.0.1 --port 8099
```

分布式模式移除 baseline 文件；切换模式会改变业务缓存、预留和消息开关，应按测试计划操作。仅启动遥测组件可执行相同 Compose 参数并指定 `otel-collector tempo`。Collector 的初始化容器只设置新队列卷目录的属主，运行中的 Collector 使用镜像默认非 root 用户 10001。

访问 `http://127.0.0.1:8099/?view=metrics#runs`，选择任务并查看“指标与监控”。上方是历史任务快照，下方是本地环境实时链路，不能把当前追踪当成旧压测报告的证据。Trace ID 可从业务响应头或 JSON 日志复制；刚产生的链路需要等待 SDK/Collector 批处理。采样未命中、队列丢弃、入库失败、保留过期均可能导致查不到链路。

## 故障隔离与排查

SDK 每进程队列最多 2048 span，批次最多 256，调度间隔 1 秒；OTLP 请求超时 1 秒。业务请求不调用 force_flush，不等待导出确认。满队列允许丢弃；导出失败通过计数和 SDK 日志暴露，不能把本配置理解为零丢失承诺。Collector 队列最多 256 批次、2 个导出消费者，单次导出超时 2 秒，重试最长 60 秒；持久队列并不提供无限磁盘容量。

排查顺序：查看 UI 的 Collector/Tempo 采集状态，检查 `http://127.0.0.1:13133/` 与 `http://127.0.0.1:3200/ready`，查询 SDK 导出失败计数、Collector 的拒收/导出失败与队列指标，再检查 Tempo 数据。组件存活或指标端口可访问不能证明数据成功入库。Collector 隐私转换采用 propagate，转换失败拒收批次，避免带有未处理字段的数据入库。

## 验证证据

本阶段新增测试覆盖真实 TCP HTTP 的父子传播、SQL 和 Redis 自动 span、日志关联、上下文清理、敏感属性/异常脱敏、不可达导出器、慢导出器的满队列丢弃、受控查询、错误状态与环境隔离。22 项可观测测试与 1 项报告回归通过。测试命令：

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests/observability -v
.venv\Scripts\python.exe -m unittest discover -s performance/reports -p test_generate_report.py -v
node --check performance/web/observability.js
docker exec seckill_prometheus promtool check config /etc/prometheus/prometheus.yml
```

本地容器验证运行了独立订单 API 进程，使用真实订单路由、DTO、业务方法和 httpx 客户端调用真实库存 API。只替换该进程内的订单仓储，让不存在的商品通过订单侧检查，库存侧返回 404；断言订单持久化没有调用。没有创建订单、预留库存、重置数据或发起 k6 压测。链路包含订单 server → order.submit → httpx client → 库存 server → inventory.reserve → MySQL CONNECT/SELECT，共 8 个唯一 span，且日志与响应 Trace ID 一致。新的链路从 Tempo 原始响应检查，未包含 db.statement、db.user、http.url。

故障演练同时停止 Collector 和 Tempo 后，商品 GET 仍返回 200（一次验证约 31 ms，不能据此推算压测开销），追踪状态明确为 unavailable；随后恢复两组件。默认采样率保持 10%，独立验证进程采用 100%，现有环境的基线业务开关没有改变。

实现依据为 [OpenTelemetry Python exporter](https://opentelemetry.io/docs/languages/python/exporters/)、[FastAPI 插件](https://opentelemetry-python-contrib.readthedocs.io/en/latest/instrumentation/fastapi/fastapi.html)、[Collector 隐私转换](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.111.0/processor/transformprocessor/README.md)、[Tempo 查询 API](https://grafana.com/docs/tempo/latest/api_docs/)。版本固定后通过实际镜像与配置验证，不依赖 latest 标签。


真实 Redis 验证直接调用库存服务的 Lua 预留方法，先确认三个验证键都不存在，再执行 Lua，得到 STOCK_NOT_READY 的返回值 -1，并确认执行后键仍不存在。Tempo 中记录 validation.redis → inventory.redis_reserve → EVALSHA 三个 span，原始返回数据不包含 Redis 键值和验证 ID；现有 baseline 的 Redis 预留开关仍为 false。这个方法返回值代表业务拒绝；内部方法完成执行的 success 属性不能替代库存预留成功率指标。

[脱敏验证快照](p1-validation.json) 保存 HTTP 和 Redis 两条验证链路的 ID、父子关系、耗时与白名单属性，便于 Tempo 保留期结束后复核；它是验证证据，不是压测报告或性能基准。订单镜像内 22 项测试、用户镜像内 9 项兼容性测试通过，Collector 实际配置已运行并完成新链路入库验证。

P3 更新后的部署前提：当前 observability Compose 文件包含全环境只读审计，请先按 [P3 运行说明](p3.md) 配置 `.env.observability.local`，执行上述 Compose 命令时增加 `--env-file .env.observability.local`。当前 UI 已为独立压测、监控、Trace、日志侧栏。
