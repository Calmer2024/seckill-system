# P2 异步追踪闭环

2026-10-03 已实现并在本地部署。共用现有工程工作台 http://127.0.0.1:8099。侧边栏「压测」「监控」「Trace」为三个独立业务页面；监控/Trace 不依赖压测任务。没有新增前端项目或修改商城前端。共享包源码版本 0.3.0。

## 实现

- 两类 Outbox 增加可空 TEXT 字段 `observability_metadata`，业务记录与元数据同事务提交。序列化内容经过白名单，限制输入 2048 字符；包含稳定 UUID Event ID、Causation ID、W3C 上下文、Request ID、创建时间及最后发送上下文。业务 JSON 消息体保持原 DTO。
- API/库存处理产生新事件时生成 UUID；库存结果的 Causation ID 指向收到的订单事件。发送重试保持 Event ID，每次发送创建新的 producer span。旧 Outbox 使用包含 owner、aggregate、user、record、topic 的确定性 UUID；无 headers 的旧 Kafka 消息使用 topic/partition/offset 确定身份。
- 显式接入 Kafka producer/consumer，避免自动与手动埋点重复。消息 key 使用订单 ID，headers 只传播受控 W3C、Request/Event/Causation ID；不传播 baggage。发送配置 `acks=all`、idempotence，等待 `future.get(timeout=20)`，成功确认之后才保存 PUBLISHED。元数据随 RETRY/PUBLISHED 更新持久化，原始创建上下文保留。
- `outbox.publish` 包括发送和发布状态提交；`kafka.process` 包括 DTO 校验、业务事务、Redis 更新及 offset commit。offset commit 失败单独计数并写入 `OFFSET_COMMIT_FAILED`。失败仍遵循原有 worker 线程监督，不新增自动吞掉异常或自动重启。
- 默认超过 300 秒的 Outbox 或 Kafka 消息建立新 trace，用 Span Link 关联原始上下文；普通重试延续原上下文并链接上次发送。`SECKILL_TRACE_ASYNC_MAX_AGE_SECONDS` 可调整。恢复时从空 OTel Context 提取，避免串用线程上一条消息的上下文。支付请求建立独立链路，以订单 ID 查询生命周期。
- 两个 worker 初始化 SDK、SQLAlchemy/Redis 埋点和导出指标；空闲 Outbox 查询抑制自动 tracing，避免生成大量轮询 trace。关键业务方法新增语义 span。
- 订单/库存状态计数在事务成功提交后更新；现有幂等分支识别 duplicate，重复确认和支付结果不重复增加状态迁移。新增发布确认、消费结果、处理耗时、offset commit 失败指标。日志携带事件与追踪关联字段。
- 独立 Trace 页面增加 worker 服务筛选、订单/Event ID 查询、span 类型、Span Link 展示与跳转。查询仍固定本地 namespace/environment、有限时间窗与结果数，不接受任意 TraceQL。

## 数据库迁移与部署

新装环境的初始化 SQL 已包含列。已有环境先执行 `infra/mysql/migrations/p2_outbox_metadata.py`，以环境变量 `OBSERVABILITY_MIGRATION_DATABASE_URL` 指向主库；不要把数据库密码写到命令行或文档。

脚本获取 MySQL 命名锁，先验证全部表，再执行白名单 DDL `ADD COLUMN ... TEXT NULL, ALGORITHM=INSTANT`。覆盖 `order_db_0/1.t_order_outbox_event_0/1` 四张表及 `inventory_db.inventory_outbox_event`。已存在列会验证类型和 nullable；缺表或不兼容列终止。不回填历史消息、不加索引、不在应用启动时自动 ALTER。MySQL DDL 不是事务，部分完成可重跑；不支持 INSTANT 时显式失败，由运维安排迁移窗口。

迁移完成后刷新 ShardingSphere 元数据（本地通过重启 proxy），再滚动重建订单/库存 API 与 worker。应用回滚可以保留可空列，避免删除已保存证据。本地迁移首次变更 5 张表，重跑变更 0 张且验证 5 张。

保持现有业务模式部署：

```powershell
docker compose -f docker-compose.yml -f performance/config/docker-compose.baseline.yml -f docker-compose.observability.yml --profile monitoring build order_service order_worker inventory_service inventory_worker
docker compose -f docker-compose.yml -f performance/config/docker-compose.baseline.yml -f docker-compose.observability.yml --profile monitoring up -d --no-deps --force-recreate order_service order_worker inventory_service inventory_worker
```

本次本地环境仍为 baseline，各优化开关为 false；没有启动 k6 或重置压测数据。Collector 保留受控 messaging、order、attempt 属性和 SDK 已过滤的 links。生产的采样/鉴权/保留与容量仍按后续阶段实施。

## 验证与证据

`python -m unittest discover -s tests/observability -v`：27 项通过。包括独立 OS 进程之间 SQLite Outbox 持久化与恢复、发送确认失败/重试、重试关联、真实 repository 重复状态迁移、提交失败不计数、支付独立 trace、实际 consumer 循环的业务/offset 失败、旧消息兼容、无上下文串线、延迟 root/link、恶意 headers 与查询参数、P0/P1 回归。

`p2_kafka_smoke.py` 使用 5 个全新容器进程、真实本地 Kafka/Collector/Tempo、专用 `p2-validation-*` topics/groups 和独立 SQLite 文件。业务 Repository、Publisher、Consumer 使用实际代码；没有写入已有 MySQL 订单/库存。完成 order create → order publish → inventory consume → inventory publish → order consume，订单最终 CREATED。实际 HTTP 入口跨服务验证由 P1 保留，P2 此次从真实订单 Repository 的持久化阶段接续验证，未进行在线下单。

链路 `1702577f275d4ec6c6a695599bf0fa99` 共 28 个 span，含 order-api/order-worker/inventory-worker；两个消费 span 的 parent 均为对应发送 span。订单 ID `999800001` 查询命中，实际 UI 已验证瀑布图与属性。另用仅合成元数据、不写业务数据的 `p2_link_smoke.py` 验证 Collector/Tempo 的 delayed Span Link 保留；UI 可点击链接返回原始链路。

原始验证摘要保存于 [p2-validation.json](p2-validation.json)，界面证据 [p2-ui.jpg](p2-ui.jpg)。Tempo 当前保留 24 小时，之后这些 Trace ID 可能查不到；静态证据仍可查看。部署后 9 个服务目标正常，两个 worker 的 5 个任务 alive=1。

进程 Counter 用于趋势，存在事务提交后进程退出的计数窗口；Kafka producer idempotence 也不提供跨 Outbox 提交与 offset 提交的 exactly-once。重复消费测试验证现有顺序幂等行为，不声称解决所有业务并发竞争。原有 business exporter 的积压指标继续使用其压测范围；环境级积压新鲜度、集中日志、告警投递和完整生产故障演练留待 P3/P4。

传播实现依据 [OpenTelemetry messaging spans](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/) 与 [Kafka producer API](https://kafka-python.readthedocs.io/en/master/apidoc/KafkaProducer.html)，具体兼容性以项目固定 kafka-python 3.0.11 和此次真实发送验证为准。


## 页面边界修正

同一个前端平台共用外壳与侧边栏，业务入口独立。`/#runs` 仅包含任务、报告、该次压测指标快照、校验和运行日志；`/#monitoring` 查询环境实时状态；`/#traces` 提供环境链路查询。后两者直接访问或刷新均不要求选中 run，不调用压测历史来建立页面上下文。环境 API 使用 `/api/observability/status` 与 `/api/observability/traces`，旧 `/api/performance/observability/*` 作为兼容别名保留。切换页面时停止相应监控轮询，sidebar 当前项、标题与浏览器前进/后退同步。
