# P3 日志与告警

2026-10-03 已实现并在本地部署。现有工程工作台 http://127.0.0.1:8099 的「压测」「监控」「Trace」「日志」是四个独立侧栏页面。监控 / Trace / 日志不依赖任务，压测详情只保存历史任务指标。没有另起前端工程或接入商城前端。

## 实现与查询范围

- Alloy v1.10.2 → Loki 3.5.3：Docker API GET 代理、私有发现网络、本项目 service 白名单；持久 positions 与 WAL。仅四个资源索引标签 namespace/environment/service/instance，Loki 自身追加 service_name；业务 ID 只在正文检索。共享 JSON formatter 和采集管道脱敏。Nginx JSON 只写路由模板，不写 query/body/原始客户端 IP；上游合法 Trace ID 关联到访问日志。原始 stderr 不上传。
- 工作台日志查询固定 Loki、固定 namespace/environment；service/level 枚举，Trace ID / 订单 ID / Event ID / Request ID 精确过滤，正文有限长度字面检索。时间窗 5/15/60 分钟，最多 200 条、响应最多 2MB、后端超时 2.5 秒。Trace → 日志以 span 时间为锚点，限三天保留范围且单次最多一小时；日志 → Trace 独立跳转。业务未采样仍可有日志。
- 监控页在平台内绘制六组真实时间序列，另列服务与后台任务状态、活动告警和持久通知。缺失、NaN、查询失败、审计过期分别处理，不补成零值。
- 全环境只读 business-audit 每三十秒巡检，跨主库全部四张订单、四张订单 Outbox、库存表及库存 Outbox 使用一个一致性快照。专用账号十表 SELECT、最多两个连接，输出负库存、PENDING 年龄、Outbox pending/最老年龄及 freshness；全部成功才替换证据。没有 product/user/run 标签。现阶段不声称已经实现全量订单预留对账或 cohort SLO。
- Prometheus → Alertmanager v0.28.1 → 本地 SQLite 通知接收器。按环境/服务/告警分组，依赖抑制，触发与恢复均投递；提交成功后 ack、去重、七天 / 一万条保留、失败重试。活动告警和已送达通知是两个独立状态。
- 规则覆盖遥测 down/missing、worker down/stalled、HTTP 系统错误、有限业务 group/topic lag、DB 连接压力、负库存、订单等待、Outbox 延迟、业务证据过期、日志丢弃 / 重试、Trace 导出失败、通知投递失败。HTTP 要求样本量；库存 / Outbox 规则要求证据新鲜。现阶段固定阈值是诊断规则，生产 SLO 多窗口 burn rate 留待 P4 校准。
- Grafana 增加 Prometheus/Tempo/Loki/Alertmanager datasource 与 Trace↔日志关联、环境总览和五组详细看板：API RED、Dependencies、Messaging and Workers、Business Evidence、Telemetry Pipeline。原压测看板保留。

## 部署

先完成 P2 的表结构迁移。运维给 `infra/mysql/migrations/p3_audit_account.py` 提供环境变量 OBSERVABILITY_ADMIN_HOST / PORT / USER / PASSWORD 和 OBSERVABILITY_AUDIT_PASSWORD。默认管理员连接 localhost:3307；账号密码至少 24 字符，不传命令行、不输出到终端。

脚本预检查十张固定物理表，创建 / 更新专用 observability_audit 账号，撤销旧权限并授予固定 SELECT、限制连接数。它只修改自己的监控账号，不修改业务表或数据。管理员环境变量只用于该步骤，随后清除。

把同一 audit 密码写到 Git / Docker 构建忽略的 `.env.observability.local`，唯一一行格式 `OBSERVABILITY_AUDIT_PASSWORD=<实际密码>`。本地本次已生成并完成授权；不要覆盖为不同密码。生产使用 secret manager 并限制宿主访问文件。

```powershell
docker compose --env-file .env.observability.local -f docker-compose.yml -f performance/config/docker-compose.baseline.yml -f docker-compose.observability.yml --profile monitoring build business-audit alert-receiver
docker compose --env-file .env.observability.local -f docker-compose.yml -f performance/config/docker-compose.baseline.yml -f docker-compose.observability.yml --profile monitoring up -d loki alloy docker-log-proxy alertmanager alert-receiver business-audit
docker exec seckill_prometheus promtool check config /etc/prometheus/prometheus.yml
Invoke-RestMethod -Method Post http://127.0.0.1:9090/-/reload
docker exec seckill_nginx nginx -t
docker exec seckill_nginx nginx -s reload
docker restart seckill_grafana
```

初始化容器负责新持久卷权限；不要让 Loki / 通知接收器以 root 运行。自定义 Compose 项目名需设置 COMPOSE_PROJECT_NAME 与 -p 一致。当前业务是 baseline，更新时保留 baseline 文件；不能因部署监控切换优化开关。

控制器需在没有活动压测时重启，仍只绑定 127.0.0.1:8099。`run-test.ps1 -WithMonitoring` 从本地忽略文件读取已知 audit 密码并让其子进程继承，避免 Python 辅助脚本的 Compose 调用丢配置；监控账号缺失时在业务动作前失败。不要运行压测来验证部署。

API：`/api/observability/logs`、`metrics`、`alerts`、`status`、`traces`、`traces/{id}`。不开放任意 PromQL/LogQL、任意后端地址或写告警管理操作。固定 [排障手册](p3-runbooks.md) 也由控制器在 `/docs/observability/p3-runbooks.md` 提供。

## 验证与证据

- 36 项共享包 / 消息 / 状态 / Trace / 日志查询 / 持久通知回归通过；新规则 promtool 单测覆盖过期证据不报负库存、外国 topic/group 不误报、本地新鲜负库存可触发。Prometheus 配置和 Nginx 配置校验通过。
- [同步日志 / Trace 证据](p3-correlation.json)、[Loki 停止 + Alloy 重启恢复](p3-outage-recovery.json)：合成探针通过真实 Collector/Tempo 与 Docker→Alloy→Loki，不写业务数据库或 Kafka。断链时日志 API 返回 503，恢复后探针可查；直接检查原始 Loki 也没有测试密码、Token、邮箱、手机号。索引标签无业务 ID。
- [日志轮转](p3-rotation-validation.json)：独立合成容器配置 json-file 2KiB、3 文件，生成 80 条长日志后最后探针仍可集中查询，验证后移除该测试容器。这只证明在线采集能跨轮转收到末尾，不能证明采集器长期离线时无限补齐已删除文件。
- [告警可达](p3-notification-validation.json)：临时 Prometheus 规则实际触发，再让条件为 false，接收器收到 firing/resolved；移除临时规则，持久记录经容器重建保留。本地启动期间的真实 BusinessEvidenceStale 也有触发和恢复记录。测试通知是明确标记的合成通知。
- 专用 DB 账号验证十个 SELECT 授权，写入与无关 mysql.user 读取均被拒绝；Docker 代理 POST 实测 403。业务请求只做商品 GET 验证，未创建订单、支付或重置数据。
- 浏览器验证独立侧栏、环境页面无需 run、日志按 Trace ID 筛选、日志→Trace→发生时段日志双向跳转。界面证据：[日志](p3-logs-ui.jpg)、[监控](p3-monitoring-ui.jpg)。

## 保留与限制

本地 metrics/trace 保留 24 小时，Loki compactor 保留三天，通知七天 / 最多一万条；都有持久卷。Loki 文件系统保留不是磁盘容量配额，要监控 Docker 宿主可用空间。各新增组件有 CPU / 内存额度和 Docker 日志轮转；仍共享开发机器与 Docker 故障域，没有生产高可用。

Alloy WAL 在锁定版本中属于实验特性，显式启用 experimental，升级前复跑恢复测试。WAL segment 最长一小时、队列 4MiB，导出重试有上限；磁盘满、采集前轮转、超过恢复窗口仍会丢失。不能保证零丢失。[Alloy WAL 官方说明](https://github.com/grafana/alloy/blob/v1.10.2/docs/sources/reference/components/loki/loki.write.md)、[Loki 保留说明](https://grafana.com/docs/loki/latest/operations/storage/retention/)。

已验收的投递渠道只有本地工作台。外部邮件 / IM / 值班路由、平台登录/RBAC、多租户、跨主机 mTLS、对象存储、多副本、容量压测、磁盘耗尽及生产故障演练均需后续生产配置 / P4 工作；本次不把这些宣称为完成。
