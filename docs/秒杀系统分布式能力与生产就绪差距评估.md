# 秒杀系统分布式能力与生产就绪差距评估

评估日期：2026-09-30。范围：当前工作区源码、Compose 配置与性能工具；包含尚未提交的改动。方法：静态代码审查，未启动集群或执行压测。因此，下文的“已实现”表示代码中有相应机制，不表示已验证生产容量或故障恢复效果。

## 结论

当前系统具备**单机 Compose 环境中的分布式机制原型**：商品读扩容、缓存保护、主从读写分离、订单逻辑分片、库存原子预扣、Kafka 异步处理及 Outbox。但安全边界、库存与订单最终一致性、真实支付、故障自愈和跨主机高可用均未达到大型生产系统的上线要求。**现状不宜承接真实资金或大流量公开秒杀。**

## 距离生产上线的阻断项

以下优先级按真实用户、真实库存和真实资金的上线场景判定。P0 必须在开放真实流量前关闭；P1 必须在大型分布式部署前关闭。

| 优先级 | 差距与可复现风险 | 完成标准 |
|---|---|---|
| P0 | **鉴权越权。**订单接口只要传 `X-User-ID` 就跳过 JWT；订单列表还允许登录用户指定任意 `user_id`。库存内部预留、取消接口也没有服务身份验证；商品预热接口公开可调用。[鉴权](../order_service/app/core/security.py)、[订单路由](../order_service/app/api/routes.py)、[库存路由](../inventory_service/app/api/routes.py)、[商品路由](../product_service/app/api/routes.py) | 移除生产环境 `X-User-ID` 后门；订单列表只能取当前主体，管理查询单独授权；内部接口使用服务间认证与网络隔离；预热接口限管理员。加入越权回归测试。 |
| P0 | **库存与订单跨服务失败窗口。**库存先预留，订单后落库；订单落库失败时靠同步取消，取消再失败只记录日志。`RESERVED` 没有过期扫描、对账和自动补偿；异步消息长期无法处理时会占库存。[订单提交与补偿](../order_service/app/application/services/order_service.py)、[预留状态](../inventory_service/app/services/inventory_service.py) | 为预留设置业务截止时间；定时扫描孤儿预留和超时订单；按订单最终状态幂等取消或确认；故障注入后自动收敛，库存守恒且无长期悬挂记录。 |
| P0 | **Redis 库存镜像可能失真。**缓存缺失时 `exists` 后直接 `set` 数据库可用库存；并发装载可覆盖已扣减值。Redis 扣减与 MySQL 写入、确认、回补失败也没有持续对账。[库存缓存](../inventory_service/app/services/inventory_service.py) | 用受控预热或原子初始化代替并发 `exists`/`set`；建立 Redis、库存账本、预留记录对账和修复；并发重启及 Redis 丢数据场景验证不超卖、不长期误售罄。 |
| P0 | **支付只是模拟。**`PAYMENT_REQUESTED` 被本地消费者直接写成 `SUCCESS`，没有支付渠道回调、验签、幂等账本、退款和对账。[支付消费者](../order_service/app/application/services/order_service.py) | 接入真实支付网关及可信回调；处理超时、重复通知、退款；金额与订单绑定不可变；完成资金账实对账后才可宣称真实交易闭环。 |
| P0 | **生产凭据与传输安全缺失。**Compose 中有固定数据库、JWT、Grafana 凭据；Nginx 仅监听 HTTP，Redis/Kafka/MySQL 为开发式明文配置，数据库和 Redis/Kafka 端口暴露到宿主机。[Compose](../docker-compose.yml)、[Nginx](../nginx.conf)、[ShardingSphere 权限](../infra/shardingsphere/conf/server.yaml) | 轮换并从代码移除凭据；密钥托管、最小权限账号、TLS、私网访问、端口收敛；完成安全审计和渗透测试。 |
| P1 | **单机与单点。**Nginx、MySQL 主库、Redis、Kafka、ZooKeeper、ShardingSphere Proxy、订单/库存服务与 worker 都只有单实例。两个订单逻辑库共享同一 MySQL 主机；Compose 没有 MySQL/Redis/Kafka 持久卷声明。[Compose](../docker-compose.yml)、[分片规则](../infra/shardingsphere/conf/config-sharding.yaml) | 跨故障域部署，数据库自动故障切换与持久备份，Redis/Kafka 高可用，入口与 worker 多副本；实测单节点故障仍满足目标 RTO/RPO。 |
| P1 | **扩容与消息可靠性边界。**主题创建为 1 分区、1 副本；Outbox 发布器直接轮询 `NEW/RETRY`，无认领/租约，多 worker 会重复发布；重试无上限、死信队列和隔离机制。[主题与发布器](../order_service/app/application/services/order_service.py)、[库存发布器](../inventory_service/app/services/inventory_service.py)、[Kafka 配置](../docker-compose.yml) | 分区键与容量规划；Outbox 原子认领和租约恢复；消费者持久幂等键；有界重试、死信与人工重放；多 worker 并发和重复投递验证最终状态一致。 |
| P1 | **热点限流与过载保护缺失。**Nginx 未配置秒杀限流；订单链路每请求同步访问商品库、库存 HTTP、Redis 和 MySQL，Kafka 只异步处理后半段。[Nginx](../nginx.conf)、[下单流程](../order_service/app/application/services/order_service.py) | 活动级准入/令牌、用户与 IP 维度限流、排队上限、负载退化与熔断；在目标峰值和依赖故障下延迟、错误、资源使用保持在约定 SLO 内。 |
| P1 | **发布和数据变更不可控。**商品服务启动时 `create_all`、改表、批量 upsert 并清空商品缓存；用户服务启动时建表并改表；缺少独立版本化迁移。两个商品实例同时启动会重复执行。[商品启动](../product_service/app/main.py)、[商品引导](../product_service/app/bootstrap/catalog_bootstrap.py)、[用户启动](../user_service/main.py) | 迁移从应用启动分离；向前兼容的版本化 DDL；发布、回滚、种子数据和缓存失效有独立流程与审计。 |
| P1 | **订单状态与业务账本不完整。**没有待支付超时关单、退款/取消后回补、异常单修复流程；商品表 `stock` 与库存账本分离，商品详情库存可能陈旧。[订单状态逻辑](../order_service/app/application/services/order_service.py)、[商品模型](../product_service/app/models/product.py)、[库存模型](../inventory_service/app/models/inventory.py) | 明确状态机和每条跨服务补偿路径；统一可售库存口径；建立订单、支付、预留、库存四账定时对账及可审计修复。 |
| P1 | **容量和故障指标尚未证明。**仓库有 k6 场景与校验器，但未见已保存的目标环境测试结果；本地单机压测不能推导生产容量。Prometheus/Grafana 在可选 profile，现有规则只有 HTTP 错误率和 Kafka lag。[性能说明](../performance/README.md)、[规则](../performance/monitoring/prometheus/rules/performance.yml) | 先定峰值 RPS、库存规模、p99、成功率、积压恢复时间、RTO/RPO；在隔离且同构环境跑阶梯、突刺、长稳、故障注入；保存报告并建立发布门禁。 |

## 建议实施顺序

1. **先封风险入口。**修复越权、内部接口认证、凭据和 TLS；把模拟支付与真实交易严格隔离。
2. **再封一致性缺口。**库存预留超时补偿、Redis 原子初始化、四账对账；用重复投递、超时、重启和部分失败用例证明收敛。
3. **再做高可用与过载控制。**跨主机部署和持久备份，多副本 worker、Outbox 认领、限流与熔断。
4. **最后用证据决定容量。**定义 SLO，在生产同构环境完成压测、演练、回滚和恢复验收；以实测报告确定可上线规模。

本报告是基于代码的就绪度判断。实际承载量、复制延迟、故障恢复时间和数据丢失窗口均需运行态测量，不能从当前配置推算。
