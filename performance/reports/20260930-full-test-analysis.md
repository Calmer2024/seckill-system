# 秒杀系统完整压测分析报告

测试日期：2026-09-30（Asia/Shanghai）
测试环境：本机 Docker Compose，入口 `frontend_nginx`，由压测平台调用 k6 0.54.0，启用 Prometheus 与业务一致性校验。
结论：商品查询、流量洪峰和一小时只读稳定性测试通过；1,000 用户争抢 100 件库存时，订单与库存状态未收敛，系统不能据此宣称秒杀链路通过。

## 测试范围与判读口径

本次执行了平台四种场景，其中商品查询分别运行基线和分布式模式，共五场。每场使用隔离测试商品 `900001`、初始库存 100、用户 ID `9000001–9001000`；每场开始前重置该范围。所有测试均通过平台 API 发起，启用监控，使用现有镜像。默认场景流量未改动：商品查询阶梯加压 2 分 30 秒，秒杀 1,000 VU 各请求一次，洪峰 22 秒，一小时稳定性测试维持 300 次/秒。

k6 的 RPS 和延迟是客户端观察值。Prometheus HTTP 指标是服务端采样值，受抓取间隔、统计窗口及直方图桶边界影响；两者不直接作数值相减。`http_req_failed` 将售罄返回的 409 也计为 HTTP 失败，须区分预期业务拒绝与 500 异常。

### 商品查询对比

两组接受相同阶梯流量，实际平均 RPS 都约为 275，均无错误。分布式模式 p95 从 2.70 ms 降至 1.93 ms，下降 28.4%；p99 从 3.38 ms 降至 2.43 ms，下降 28.2%。分布式报告的商品缓存命中率为 100%。测试只访问一个预热后的测试商品，因此该命中率不能代表真实商品目录或冷启动表现。本测试由指定到达率控制请求量，不能据此推断系统最大吞吐能力。

### 秒杀库存争抢：阻断性失败

1,000 个用户同时争抢 100 件库存。k6 记录 100 次接单、798 次售罄拒绝、102 次其他拒绝。Prometheus 将后者对应到 102 个 500 响应；798 个 409 是库存售罄的预期业务结果。真正异常的 500 比例为 10.2%，而 k6 的 90% HTTP 失败率包含两者。无请求超时，但 p95 响应已达 5.74 秒。

[运行结束校验](runs/20260930-085530-7e1928/validation.json)显示：库存 `available=95`、`reserved=-96`、`sold=100`，三者合计 99，既有负库存状态也不满足初始总量 100；100 条库存预占均已确认，但有效订单数为 0；库存 Outbox 仍有 100 条待发消息。重复活动订单数为 0。稍后执行的[复核](runs/20260930-085530-7e1928/validation-late.json)仍得到相同状态，排除了单纯等待不足的解释。

主库配置 `max_connections=151`，压测时 `Max_used_connections=152`；订单服务和库存发布线程日志出现 MySQL `1040 Too many connections`。库存发布线程因未处理的数据库连接异常退出，能直接解释 Outbox 无法排空及订单未获库存确认结果。数据库连接池配置的总潜在连接数高于主库上限，1000 VU 同时进入时暴露该容量不匹配。

负预占库存和库存总量不守恒仍需单独定位。代码中预占采用条件 SQL 更新，而确认与取消路径读取库存对象后执行字段加减并提交；并发更新竞争是合理怀疑，但本次证据尚不能唯一确定其根因。不得将此问题仅归因于连接耗尽，也不能将“售出数恰为 100”理解成库存链路正确。

### 流量洪峰

场景在 2 秒内升至目标 2,000 次/秒，保持 10 秒，再于 10 秒内降至 0。22 秒完成 32,000 次请求，无丢失迭代、HTTP 错误或超时；p95 为 3.39 ms，p99 为 6.67 ms。整段平均 1,454 RPS 包含升降阶段，不能拿来当平台期吞吐。Prometheus 原报告的 `http_rps_peak` 采用 1 分钟 `rate` 窗口，短于 1 分钟的场景会被窗口摊薄；对同一时间段改用 15 秒窗口查询，观测峰值约 1,853 RPS。此值仍是窗口平均值，不等于 k6 瞬时目标 2,000 RPS。

### 一小时稳定性

一小时混合读取流量约 80% 商品查询、20% 库存查询，总计 1,080,001 次，实际 300.01 RPS；零 HTTP 错误、零超时、零丢失迭代，一致性校验通过。Prometheus 同一服务端口径下，17:15 与 18:00 的 5 分钟窗口 RPS 分别为 300.08 与 300.00，p95 分别约 4.750 与 4.753 ms，均未表现出明显恶化。

同两时点容器工作集内存：商品实例分别由 284.2/283.7 MiB 至 285.3/285.1 MiB；库存服务由 120.1 至 138.2 MiB；MySQL 主库由 609.8 至 667.5 MiB。商品实例基本稳定，库存服务和数据库有一定增长，但仅凭一小时内存变化不足以判断泄漏；需要结合更长周期、GC 与数据库缓存指标复核。

## 结论与后续优先级

1. **P0：修复秒杀一致性。** 先限制连接池总量与 MySQL 上限的关系，为库存 Outbox 发布线程加入数据库异常恢复，再针对库存预占、确认和取消的并发更新做状态不变量复测。复测必须验证有效订单数、已售数、确认预占数相等，预占非负，库存总量守恒，Outbox 排空。
2. **P1：重测争抢阶梯容量。** 从低并发逐级升至 1,000 VU，分别记录首次 500、连接数、p95 与状态收敛点。当前结果只说明 1,000 VU 下失败，不足以确定安全上限。
3. **P2：补充更接近真实业务的读流量。** 商品查询应覆盖多商品和冷热缓存，分别测量缓存命中率与数据库负载。当前单商品热缓存结果仅证明该条件下的表现。
4. **P2：修正短场景峰值口径。** 对小于 1 分钟的洪峰场景展示 10–15 秒速率窗口，并明确其为窗口平均值。

本机 Docker Desktop 同时承载负载生成器、网关、数据库、消息队列及监控。本报告适用于本地瓶颈定位和正确性判断，不能直接外推生产容量。

测试结束后已重启曾退出发布线程的库存 worker；日志确认发布线程与订单消息消费线程重新启动。[测试后状态校验](post-test-validation.json)通过，隔离商品库存为 `100/0/0`，订单与 Outbox 均为 0。这是环境恢复检查，不改变争抢场景的失败结论。
